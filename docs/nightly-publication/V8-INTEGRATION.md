# Signed producer integration — private source, publication off

The live publisher and attestation CLIs require the original signer receipt by exact artifact ID and independent signer hash, bind identity/tooling/run/unsigned/final hashes and configured publisher, rehash the final package and accept only the explicit craft-nightly/v2 descriptor. Offline v1 helper APIs remain only to preserve historical diagnostic fixtures; the new live CLIs have no v1 fallback. Descriptor parsing is not OS signature verification. Windows Authenticode verification occurs in the isolated signing job before final repack/hash; downstream Ubuntu jobs trust that source-bound signer output and recheck exact bytes, not an invented Linux Authenticode pass.

After an exclusive201 tag creation and verified successful publish, the publisher emits ownership.json. Its unique immutable Actions artifact is uploaded in the same job only after Publish. Historical ownership verification checks authenticated workflow/job/step/run/artifact metadata plus reviewed tooling source; GitHub provides run-level artifact origin, not platform-signed job/tag creator attestation. Unknown/expired/ambiguous ownership preserves or refuses, never grants deletion.

Pruning is wired after publication but its planning step is independently literal false. When explicitly activated for the approved first manual run, planning completes and the exact plan is uploaded immutably BEFORE apply. Apply authenticates numeric artifactID, independent upload digest, repository/run/attempt/head/callee origin and downloaded exact plan bytes; only then invokes the full keep-seven candidate/ownership/ref preflight and release-first/tag-second executor. Local fsync alone is not treated as durable. A deleted-release/remaining-tag recovery reuses the same plan and authenticates historical ownership again; a fresh plan never scans/adopts orphan refs. Checkpoint retention is90days; unavailable artifacts refuse and require explicit reconciliation. No source test is a live delete test.

V2 reviewed-baseline bootstrap is wired to NIGHTLY_REVIEWED_POLICY_SHA256 from trusted repository/environment configuration, never computed from candidate JSON as its own authority. Runtime still refuses incomplete inventory. IMPORTANT: the strict Actions baseline adapter currently refuses skipped/trigger-dependent obligations and unknown external checks; the real Photo SonarCloud external-app check has no implemented applicability adapter. This remains a source integration blocker to a runnable first publication, not a claim the existing main is permanently red or that unknown checks can be ignored. A maintainer-reviewed complete baseline plus independent review digest/refresh history and explicit applicability design are required before activation. Sonar historical shard-test and corrupt-profile failures are separate evidence; no unrelated profile dropping/fix is invented.

Linux and macOS build/sign paths are authored but stay disabled/unadmitted pending the actual isolated app adapters, independently configured key/publisher/TeamID trust and native/consumer checks. Linux uses stable’s OpenPGP ASCII archive.asc scheme with16KiB cap and reviewed public key/full primary fingerprint; downloaded release keys never establish trust. Mac requires DeveloperID/team/runtime/timestamp/notarization/staple/Gatekeeper checks with no unsigned fallback.

No real credentials were read, signing was mocked, no hosted workflow/settings/push/PR/release/deletion was performed. Published tooling/caller pins, public secret/environment/protection configuration and first-run timing remain separate approved operations. Existing stable release workflow and all historical8db/f0 fixture bytes remain unchanged.
